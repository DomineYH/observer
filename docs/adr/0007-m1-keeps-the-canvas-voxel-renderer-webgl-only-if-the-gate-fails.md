# M1은 캔버스 보셀 렌더를 그대로 옮기고, WebGL 전환은 성능 관문에 떨어질 때만 판단한다

PRD 7.3은 "목표에 못 미치면 지형 렌더를 WebGL 셰이더로 옮긴다"고 했지만 목표도 판단 시점도 없었다. 실제 기기에서 잰 데모 v0.2는 높음 화질(640×360)에서 PC(Intel Core i5-10210U, 내장 그래픽, Chrome) 51/42 fps, Xiaomi 14T(Chrome) 50/60 fps(육안/쌍안경)였다. 성능 목표를 "기준 기기 두 대에서 기본 화질(높음)로 육안·쌍안경 모두 30 fps 이상"으로 잡으면 CPU 렌더로 이미 넘는다. 그래서 M1은 데모의 캔버스 보셀 렌더(화면 열마다 앞에서 뒤로 훑기 + 도트 후처리)를 TypeScript로 그대로 옮기고 WebGL을 쓰지 않는다. M1 안에서는 WebGL 전환을 판단하지 않는다.

성능 목표는 M1 끝의 사람 검수에서 기준 기기 두 대로 잰다. 못 미치면 먼저 기본 화질을 보통(480×270)으로 내려 다시 재고, 그래도 못 미칠 때 비로소 WebGL 전환을 새 결정으로 연다. 화질 자동 하향은 넣지 않는다. 화질은 플레이어가 메뉴에서 고른다.

## Considered Options

- **M1부터 WebGL**: 데모와 픽셀 단위로 같은 그림(양자화·디더링·능선 윤곽)을 셰이더로 다시 짜야 하고, 잰 값으로는 얻을 것이 없다.
- **렌더러 이음매를 미리 두고 둘 다 지원**: 쓰이지 않는 추상화다. 렌더러는 이미 시뮬레이션 상태를 읽기만 하므로 나중에 통째로 바꿀 수 있다.
- **화질 자동 하향**: 데모에 없는 동작이고, 하향 기준·되돌림·표시를 새로 정해야 한다. 기준 기기는 기본 화질에서 목표를 넘는다.
- **목표를 60 fps로**: 높음 화질에서 두 기준 기기 모두 못 넘어 기본 화질을 낮추거나 WebGL이 필요해진다. 시뮬레이션은 초당 20틱이라 30 fps로 조준과 탄착 관측에 충분하다.

## Consequences

- 태블릿과 보급형 휴대폰은 잰 값이 없다. 지원하지만 기준 기기가 아니며, 느린 기기의 플레이어는 화질을 보통으로 직접 내린다.
- 프레임이 느려도 시뮬레이션 결과는 같다. 프레임 간격을 0.1초로 자르고 남는 실제 시간은 버리므로 게임이 느리게 흐를 뿐 틱은 빠지지 않는다. 결정성 관문과 무관하다.
- 성능은 CI에서 재지 않는다. M1 빌드는 사람 검수용 fps 표시(`?fps=1`)를 가진다.
- PC 모니터 주사율은 기록되지 않았다. 60 Hz 화면이라면 PC의 잰 값은 60에서 잘린 값이다.
- 2026-11-11: 기준 데스크톱에서 땅을 볼 때 높음이 육안 28.5 · 쌍안경 27.5 fps로 목표에 못 미쳐(#45, 에이전트 측정), 위 절차대로 기본 화질을 보통으로 내렸다(보통 40.5 · 36.6). WebGL 전환은 열지 않는다. 데모의 기본은 높음이므로 의도된 차이다.
